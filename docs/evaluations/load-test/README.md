# F-23.3 一般 API 負載測試紀錄

測試日期：2026-11-24。對應 #113（F-23.3）。本頁記錄 S-10.2「一般 API（不含 AI）p95 ≤ 500 毫秒」在 S-10.3「約 60 人同時使用」下的量測方法與結果。AI 回應時間（首個 token、完整回覆）的真實模型抽樣不在本頁，見文末「待確認」。

## 量測方法

測試程式在 [`backend/tests/load_test.rs`](../../../backend/tests/load_test.rs)，標成 `#[ignore]`，CI 不會跑。

- **後端是真的**：路由、登入、權限、CSRF 檢查、SQL 與 PostgreSQL 都是正式程式碼；服務開在真實的 TCP 埠上，學生用 HTTP 連進來。
- **AI 是假的**（S-10.2「一般 API 用假 AI 做負載測試」）：立即回覆一段固定的追問與總結，排除供應商延遲。
- **連線池與正式環境相同**：`max_connections(10)`（`main.rs`）；AI 逾時用正式值（首個 token 15 秒、完整回覆 60 秒）。
- **全班同時開始**：60 位合成學生（`load{n}@example.com`）在同一個時間點一起出發，每人各自一個 HTTP client（各自的連線），模擬整班一起上課。
- 每位學生的流程：登入 → `GET /api/me` → `GET /api/catalog` → `GET /api/conversations` → 從活動開始對話 → 送出 3 則訊息（SSE）→ 看對話 → 結束對話 → 看總結 → 再看一次對話列表。
- **判定值**：所有一般 API 請求合在一起的 p95（nearest-rank）。送出訊息只計到「學生訊息已保存」（第一個 SSE 事件，AI 還沒開始）；「串流結束」含 AI 回覆，另列，不算一般 API。
- 每次執行建立一個全新的資料庫，量完刪除；只用合成資料，不連任何部署環境。

執行方式（在 `backend/`，需要 `DATABASE_URL` 指到可建立資料庫的 PostgreSQL，例如 `docker compose up -d --wait` 那一個）：

```bash
cargo test --release --test load_test -- --ignored --nocapture
```

可調整：`LOAD_USERS`（同時學生數，預設 60）、`LOAD_TURNS`（每人訊息數，預設 3）、`LOAD_AI_DELAY_MS`（假 AI 每個片段前的等待，預設 0）。數字要用 release 建置量；debug 建置會明顯偏慢，輸出會提醒。

## 結果

環境：雲端容器，2 核 Intel Xeon 2.30GHz、7 GB 記憶體；PostgreSQL 16.15 與後端在同一台；Rust 1.97.0 release 建置；main 為 `b66a43e`。

### 60 人、每人 3 輪、假 AI 立即回覆（S-10.3 的設計情境）

| 請求 | 次數 | 錯誤 | p50 (ms) | p95 (ms) | 最大 (ms) |
| --- | --- | --- | --- | --- | --- |
| 登入（Google callback） | 60 | 0 | 83.8 | 95.6 | 107.7 |
| GET /api/me | 60 | 0 | 44.4 | 51.3 | 52.2 |
| GET /api/catalog | 60 | 0 | 50.0 | 56.2 | 58.1 |
| POST /api/conversations | 60 | 0 | 151.4 | 206.3 | 209.0 |
| POST messages：學生訊息已保存 | 180 | 0 | 31.2 | 158.3 | 194.3 |
| POST messages：串流結束（含假 AI） | 180 | 0 | 74.1 | 201.5 | 240.6 |
| GET /api/conversations/{id} | 60 | 0 | 26.6 | 82.0 | 83.9 |
| GET /api/conversations | 120 | 0 | 29.8 | 37.4 | 113.0 |
| POST /api/conversations/{id}/end | 60 | 0 | 45.8 | 86.8 | 89.0 |
| GET /api/conversations/{id}/summary | 60 | 0 | 53.5 | 85.7 | 98.4 |

**一般 API 整體 p95：159.0 ms（門檻 500 ms），錯誤 0 次，達標。**

### 補充情境（雲端容器）

| 情境 | 一般 API 整體 p95 | 錯誤 | 說明 |
| --- | --- | --- | --- |
| 60 人，假 AI 每個片段等 1 秒（每則回覆約 3 秒） | 69.3 ms | 0 | AI 串流長時間佔著連線時，其他請求不受影響 |
| 120 人（兩倍班級），假 AI 立即回覆 | 163.5 ms | 0 | 兩倍人數仍遠低於門檻 |

60 人同時登入沒有被登入的 IP 限流擋下（同一個 IP 發出，比照校園 NAT）。

## 限制

- 後端、資料庫與負載產生器在同一台 2 核機器上，彼此搶 CPU；正式部署的數字會不同。正式環境的部署方式尚未決定（S-09.1），在那之前這份結果只代表「程式本身在 60 人下沒有瓶頸」。
- 只量 API，不含頁面載入（LCP p75 ≤ 2.5 秒）與語音備援（S-10.2 另兩項門檻）。
- 背景的結構化 AI 呼叫（主張分組等）由假 AI 回最小 JSON，不代表真實 AI 的背景負擔。
