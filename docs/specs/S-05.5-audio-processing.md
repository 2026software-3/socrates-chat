# S-05.5 麥克風前處理與開口打斷

語音對話的麥克風前處理、AI 播放中的開口打斷，以及 SpeexDSP 的評估。決策摘要見 [`decisions.md`](decisions.md) S-05.5；S-05.2 的回合規則與 S-05.4 的「不保存音訊」不變。

本文描述瀏覽器路徑。部署方啟用伺服器端語音對話時，語音對話改走 [`cascade-voice-spike.md`](cascade-voice-spike.md)，音訊會上傳；麥克風前處理規則相同，開口偵測與回合規則以該文件為準。

資料查證日期：2026-11-01。相容性資料來自 MDN browser-compat-data 8.1.7（2026-10-22）與各瀏覽器原始碼（開發主線，不等於穩定版已出貨）。

## 現有架構

| 環節 | 實作 | 能否套用前處理 |
| --- | --- | --- |
| 預設辨識 | Web Speech API，由瀏覽器自己開麥克風 | 不能。`start(track)` 只有 Chrome／Edge 桌面 135+ |
| 備援辨識 | `MediaRecorder` 錄整段後上傳 `/api/voice/transcribe` | 能，本次改用下述 `openMicrophone` |
| 預設播放 | `speechSynthesis`，回覆生成中逐句播放 | 瀏覽器不提供音訊串流，沒有回音參考可用 |
| 備援播放 | `/api/voice/speech` 取得整段音訊，用 `<audio>` 播放 | 由瀏覽器算繪，可進入回音參考 |
| 傳輸 | HTTP + SSE，**沒有音訊串流** | 不適用 |
| 後端 | `backend/src/voice.rs` 代理整段辨識與合成 | 不做音訊處理 |

瀏覽器路徑沒有 `Real-Time Audio Transport → Rust Backend → Streaming ASR`。這一段由伺服器端語音對話提供，接在分幀的 `onFrame` 之後。

## 模組邊界

```text
麥克風 ─ getUserMedia（AEC／NS／AGC）            audio/microphone.ts
   │
   ├─ 可選 DSP 階段 DspStage（目前沒有任何實作）   audio/frame-capture.ts
   │
   ├─ AudioWorklet 分幀，每幀 20 ms               public/audio/pcm-frame-processor.js
   │
   └─ 開口偵測（只在瀏覽器內，不上傳）             audio/speech-detector.ts
          │
          ▼ onSpeech
   barge-in.ts（組合以上，負責資源與競態）
          │
          ▼
   use-voice.ts（回合管理）──▶ speaker.ts ─ playback-queue.ts（播放與過期片段）
```

- 擷取、播放、回合分開：`barge-in.ts` 不碰播放，`speaker.ts` 不碰麥克風，只有 `useVoice` 知道兩者的關係。
- 幀不經過 React：`onStatus` 只在狀態改變時觸發。
- worklet 放 `public/`，維持同源網址。`CSP_DEFAULT` 是 `script-src 'self'`，`blob:`／`data:` 的 worklet 會被擋。不提供 ScriptProcessorNode 退路：所有目標瀏覽器都有 AudioWorklet。
- AudioContext 用預設取樣率，不指定 16 kHz，避免各瀏覽器的重新取樣差異；偵測器自己降頻。

## 前處理規則

1. 用 `getSupportedConstraints()` 判斷，只要求有列出的項目，不看 User-Agent。
2. 用布林值要求（`ideal`），依規格不會造成 `OverconstrainedError`。
3. 用 `getSettings()` 讀實際狀態，四種結果如下。

| 狀態 | 意義 |
| --- | --- |
| `active` | 瀏覽器回報開啟。**只代表瀏覽器這麼說，不代表有效** |
| `inactive` | 回報關閉，或是 `remote-only`（不處理本機播放） |
| `unreported` | 有列出但 `getSettings()` 沒回報，不能假設有開 |
| `unsupported` | 沒有列出，也沒有要求 |

少了任何一項都只是品質降級。語音對話畫面的「音訊診斷」顯示這些狀態，不含裝置識別資訊；失敗原因也會寫到 `console.warn`。

本次刻意不要求 `echoCancellation: 'all'`（Chrome 141+）：穩定版實際行為無法確認，而且有 issue 標題指出播放開始時可能壓掉麥克風語音達 1 秒（內文未能讀取）。

## 開口打斷

**流程**：AI 真的開始發聲時才開麥克風，音量校準才對得上播放。偵測到開口後依序：釋放麥克風 → 中斷播放並清空佇列 → `speakReply` 啟動新的辨識器 → 提示學生再說一次。辨識器從不和麥克風監聽同時運作，避開 Chrome Android、iOS 的同時收音問題。

**偵測期間的聲音會遺失**：判定開口至少要 240／360 ms，加上重新開麥克風的延遲，這段聲音都不會進辨識器，短句可能整句消失。瀏覽器的 Web Speech 不接受預先錄好的音訊，所以目前無法交接，改為明確提示（`voice.notice.bargeIn`，非錯誤樣式）。提示留到收到學生的文字、下一次播放或關閉語音對話才消失；按「停止播放」或「說話」打斷時沒有遺失，不顯示。

**不是單純音量門檻**：要同時滿足下列三項（`speech-detector.ts`）。

1. 比環境基準高出門檻；音高落在 AI 已出現過的基頻範圍（±15%）內時，再多要求 8 dB
2. 有人聲基頻（90–400 Hz）的週期性，排除鍵盤、風扇
3. 在 `2 × minVoicedMs` 內累積 `minVoicedMs`，排除咳嗽、碰撞

環境基準是「近 3 秒內累積達 300 ms 的最高音量」，且一輪播放內只升不降：AI 長停頓後回來不會被當成新聲音，咳嗽這類短聲音也不會墊高基準。音高範圍從校準與播放中未觸發的有聲幀學習。

AI 語音也有週期性，所以防止被自己打斷靠的是第 1 項。學生若沒有明顯蓋過殘響就不會觸發，這是刻意的取捨：**寧可漏判，手動「說話」按鈕永遠可用**。基準只升不降的代價也在這裡：播放初期若有持續 300 ms 的大聲音（包含學生自己沒有觸發的發言），這一輪後面都更難觸發。

**仍無法完全區分 AI 與學生**：沒有播放參考訊號，只能靠音量與音高推測。AI 忽然變大聲且音高跳出學過的範圍，仍可能打斷自己；學生音高與 AI 重疊時，要多大聲 8 dB 才會觸發。AI 音高範圍若很寬，這條規則實際上等於門檻固定多 8 dB。

**回音風險**：`getSettings()` 回報開啟不代表消得掉 AI 的聲音。

| 情況 | 風險 | 門檻（音高重疊時再加 8 dB） |
| --- | --- | --- |
| `<audio>` 播放，且 AEC 回報開啟 | 低 | 高出 8 dB，累積 240 ms |
| `speechSynthesis`，或 AEC 未開啟／未回報 | 高 | 高出 14 dB，累積 360 ms |

這些數值只用合成訊號測過，**尚未用真實喇叭、麥克風與人聲校正**。

**過期音訊**：`PlaybackQueue` 一次只服務一則回覆。打斷會中止目前片段並清空佇列，遲到的片段因回覆編號不符而被拒收；停止時尚在載入語音或等待後端的請求也不會發聲。回覆生成時逐句加入佇列，播完時若回覆還沒結束就等下一句；麥克風在一輪內只開一次，句子之間不重新校準。片段目前是文字，音訊串流 TTS 接上後規則不變。

**句子切分**：`sentence-splitter.ts` 用瀏覽器的 `Intl.Segmenter`，最後一段要等下一段出現或回覆結束，避免小數點或還沒講完的句子被切開。不支援時等回覆結束才唸。

**備援語音**：走 OpenAI 時，後端合成每個請求扣一筆與對話共用的 AI 用量，所以每則回覆最多發 3 次請求（`BACKEND_SPEECH_MAX_REQUESTS`，失敗的也算）。第一次是第一句，第二次合併當時已累積的句子，最後一次等回覆結束，把剩下的全部帶走；生成再慢也不會超過上限。學生打斷後不再發請求。代價是最後一段要等回覆生成完才開始唸。瀏覽器語音不計費，逐句播放。

**自架語音模型**：設了 `OPENAI_TTS_BASE_URL` 時，語音合成改打該服務，不送 OpenAI 金鑰、不扣 AI 用量，也不設每則回覆的請求上限：回應帶 `X-Speech-Pacing: sentence`，前端逐句送、不合併，因為本地模型長文容易失控，合併反而有害。第一個回應回來前前端不知道部署方式，但佇列要等第一句唸完才取下一句，所以標頭來得及生效。沒有用量上限擋著，改由後端限制每位使用者同時一個請求，超過回 `429 speech_busy`（暫定，待需求方確認）；限制只存在記憶體，多個實例各自計算。

**播放失敗**：合成或播放失敗時這一輪結束，輪到學生，並留著「無法播放 AI 語音」的提示。開始收音、學生開口和 30 秒的閒置提示都不會清掉它，學生關閉、下一次播放或結束語音對話才消失。回覆生成完後可以按「重播」再試，重播一次算一筆用量。

**排隊送出**：生成中打斷後，學生說完的訊息留在輸入框，等回覆結束才送出。回覆失敗時輸入框被鎖住，不能繞過它疊上新訊息，所以繼續排隊並提示學生按「重試」；重試成功後自動送出，再失敗就繼續排隊。排隊期間的回覆（包含重試的）只顯示文字不唸，因為學生已經往下說了。回覆失敗之後才說完的訊息也走同一條路。結束語音對話會取消排隊，文字留在輸入框，由學生自己決定。

**系統靜音**：軌道收到 `mute` 事件就立刻釋放麥克風，這次語音對話不再嘗試。iOS 上有多則回報指出播放語音時麥克風被靜音（見下表），這是執行時的實際行為偵測，不需要判斷瀏覽器。

**開關**：「開口打斷 AI」預設關閉，學生開啟後存在 localStorage。關閉時播放期間不開麥克風，等同舊行為。**下方的手動驗證在 iOS Safari 通過之前不得改為預設開啟**；改預設值時，要用新的規格 PR 附上實機結果，並確認曾明確關閉的學生不受影響。

## 已知限制

- **iOS Safari 是最大風險**。使用者回報指出：`speechSynthesis` 播放時 `getUserMedia` 軌道被靜音或全為零（[WebKit 218815](https://bugs.webkit.org/show_bug.cgi?id=218815)），辨識器啟動或 TTS 後軌道被靜音、「無法開口打斷」（[WebKit 321436](https://bugs.webkit.org/show_bug.cgi?id=321436)）；擷取期間音訊工作階段切成 PlayAndRecord，播放音量可能降低約一半（[WebKit 236219](https://bugs.webkit.org/show_bug.cgi?id=236219)）。最壞情況是第一次開麥克風就影響音量或後續辨識，因此功能預設關閉；開啟的學生遇到問題時，關閉開關就回到舊行為。
- AudioContext 在點擊時喚醒後會先 suspend，AI 開始說話時才沒有手勢地 resume。Safari 是否允許尚未驗證；不允許時診斷會停在「啟動中」，只是少了自動打斷。本次的真實瀏覽器驗證放寬了自動播放限制，不能當作這點的證據。
- Safari 桌面可能回傳全零樣本而不是 `mute` 事件（218815）：偵測不會觸發，也不會誤觸發，但診斷會顯示「監聽中」。
- Chrome Android 沒有硬體 AEC 的裝置，`<audio>` 不在參考內，但 `getSettings()` 仍可能回報開啟，風險會被低估。擷取中可能切到通話音量（[Chromium 原始碼](https://chromium.googlesource.com/chromium/src/+/main/media/audio/android/audio_manager_android.cc)）。
- Chromium 的相關 issue 內文無法讀取，只知標題，已標為推論或未驗證。
- `ended` 事件在麥克風拔除時是否觸發由實作決定，規格沒有保證。未觸發時偵測只是聽不到，不影響播放。
- 不監聽 `devicechange`：學生途中換預設麥克風時，下一次播放才會用到新裝置。
- 主執行緒長時間阻塞時，訊息會在佇列累積，偵測延遲但不會遺失。
- 回覆中途失敗時，已唸出的句子收不回來，學生可能聽到後來作廢的內容；重試時會從新回覆的開頭唸。
- 備援語音沒有預先載入，每段都要等合成完才播，句子之間會有停頓，長度取決於合成延遲。走 OpenAI 時一則回覆最多用 3 筆 AI 用量，比整段合成多 2 筆；一個學生用備援語音完成一輪對話，最多 4 筆（對話回覆 1 筆加語音 3 筆），還不含語音辨識。上限 3 是為了平衡開頭速度與用量的暫定值，待需求方確認。走自架模型時語音不計入用量。
- 語音用量用完時（429）依「播放失敗」處理，但同一份額度也會讓下一則對話回覆失敗。
- 連續多句 `speechSynthesis` 的句間停頓、以及在沒有使用者手勢時接續播放是否穩定，都還沒有在實機上驗證。
- `Intl.Segmenter` 依標點斷句，縮寫後接大寫字母（例如 `Dr. Smith`）可能被切開，只影響唸的節奏，不影響內容。

## SpeexDSP 評估

**結論：現在不導入。** `DspStage` 保留擴充點，目前沒有任何實作。

| 項目 | 發現 |
| --- | --- |
| 授權與維護 | BSD-3-Clause；最新 1.2.1（2022-06-24） |
| WASM | 沒有官方版本，也沒找到維護中的 AEC 移植，要自己用 Emscripten 建置並維護。在 worklet 內執行可能需要調整 CSP 的 `'wasm-unsafe-eval'`（未驗證） |
| AEC 需求 | 每一幀都要有對應的播放參考。[手冊](https://raw.githubusercontent.com/xiph/speexdsp/master/doc/manual.lyx)明言延遲超過濾波器長度就消不掉回音，收播時脈漂移會讓濾波器無法收斂 |
| 參考訊號 | **`speechSynthesis` 拿不到**：瀏覽器沒有對應的 API（[web-speech-api#69](https://github.com/WebAudio/web-speech-api/issues/69)，2019 年起未解決）。只有 `<audio>` 路徑能以 `createMediaElementSource` 取得，而那條路徑在桌面瀏覽器本來就已被原生 AEC 涵蓋 |
| 時間對齊 | 麥克風與 AudioContext 不保證同一時脈（未驗證），需自行估計延遲與漂移。分離式 API 固定假設 2 幀延遲，[標頭檔](https://raw.githubusercontent.com/xiph/speexdsp/master/include/speex/speex_echo.h)註明「可能不準」 |
| 參數 | `speex_echo_state_init` 預設 8 kHz，必須另設取樣率；幀 10–20 ms；濾波器長度約為殘響時間的三分之一；樣本為 16 位元整數 |
| 降噪 | `speex_preprocess_*` 有降噪、AGC、VAD、殘響抑制；去殘響「尚未可用」 |
| CPU | 官方沒有公開數字，未驗證 |
| 延遲 | 至少增加 1 幀（10–20 ms），分離式 API 另加 2 幀 |
| 平台 | 需要 AudioWorklet 與 WASM。與原生處理重疊的項目必須關掉，否則兩套 AEC 互相干擾 |

**不能只因為瀏覽器沒列出某個約束就啟用**：例如 Safari 沒有 NS／AGC，但它的 VoiceProcessingIO 本身可能已在處理，再疊一層未必更好。

**值得導入的條件**（全部成立才考慮）：

1. 真實裝置測試顯示原生處理不足，並且有量測數據
2. 已改用經瀏覽器算繪的播放（Web Audio 或 `<audio>`），能提供同步參考
3. 問題集中在 `getSettings()` 確認關閉、又有足夠使用者的環境
4. 已量測目標手機上的 CPU 與延遲

只需要降噪、不需要 AEC 時門檻較低，不需要參考訊號。`selectDspStages` 會略過與原生 `active` 項目重複的階段。

## 上線前的手動驗證

每個目標平台都要跑，並用「音訊診斷」記錄結果。iOS Safari 全部通過是預設開啟的前提：

1. 用喇叭播放 AI 語音，保持安靜，包含音量起伏大與長停頓的回覆：AI 不會被自己打斷
2. 用喇叭播放時開口：能打斷，門檻合理
3. 打斷後顯示「請再說一次」，再說一次時辨識正常；用短句測試遺失程度
4. 開啟與關閉開關時，AI 語音音量、音質是否有差異（iOS、Android 特別注意）
5. 拔除藍牙或 USB 麥克風：不會卡住，文字輸入可用
6. 開口打斷後再完成幾輪對話：辨識持續正常（iOS 特別注意）
7. 用多句回覆測邊生成邊唸：第一句很快開始、句間停頓可接受、不漏句也不重複；回覆還在生成時打斷並說話，訊息在回覆結束後送出
8. 在 OpenAI 備援語音路徑確認一則回覆最多 3 筆用量；用完額度時顯示「無法播放 AI 語音」，學生仍可閱讀文字
9. 在自架語音路徑確認逐句請求、不扣用量；打斷後下一輪第一句不會撞上 `speech_busy`
