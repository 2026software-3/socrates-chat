# S-09.3 migration、監控、備份還原流程與負責人

> **狀態：已確認（2026-09-29），負責人人選待定。** 依據已確認的 S-08.3（`sqlx migrate`、環境變數）、S-09.1（開發與 CI 用 Docker Compose，正式環境後定）、S-09.2（憑證由部署平台注入）。正式環境的部署方式尚未決定，因此下文分成「與平台無關」與「依平台選擇」兩部分。

## 1. Schema migration

| 項目 | 規格 |
| --- | --- |
| 位置與命名 | `backend/migrations/<timestamp>_<描述>.sql`，由 `sqlx migrate add <描述>` 產生 |
| 方向 | **只往前**（2026-11-07 起，NTNU 視為正式環境，見下方「NTNU 現況」）：已合併的 migration 不修改也不刪除，要修正就新增一個 migration，其中包含 `ALTER` 與既有資料的搬移（見 [CONTRIBUTING.md](../../CONTRIBUTING.md#資料庫-migration)）。先前「正式上線前直接修改原本的 `CREATE`、不寫 `ALTER`」的做法於這一天作廢 |
| 相容性 | 採「先擴充、後收縮」：新版程式能同時處理新舊 schema，刪欄位等破壞性變更留到下一次部署 |
| 開發環境 | 後端啟動時自動執行 `sqlx::migrate!()` |
| 正式環境 | 部署流程中先單獨執行 `sqlx migrate run`，成功後才啟動新版；應用程式啟動時**不**自動 migrate |
| CI | 啟動 PostgreSQL service container → 執行 migrations → `cargo test`；加上 `cargo sqlx prepare --check`，確認查詢快取與 schema 一致 |
| 失敗處理 | migration 失敗時中止部署，舊版繼續運作；由負責人修正後重新部署。不在正式環境手動改 schema |

### NTNU 現況（2026-11-07 決定）

- **資料保留與 migration 規則：** NTNU 試用環境（compose 專案 `socrates-ntnu`）自 2026-11-07 起視為正式環境，其資料庫的資料要保留，不再以 `down -v` 重建。這只決定上面的 migration 方向與資料保留，**不等於決定正式環境的部署方式**（S-09.1 仍待決定）。
- **已套用的 migration 不可變：** 後端以 checksum 比對 `_sqlx_migrations`，已套用的檔案內容一變就 `VersionMismatch`、後端無法啟動。
- **既有的不一致：** F-29.1（#458）曾直接修改已套用的 `20261002010000_create_topics_activities.sql`（把 `activities.topic_id` 改成 `activity_topics`）。補救方式是還原該檔，並由 `20261107000000_create_activity_topics.sql` 新增 `activity_topics`、把既有活動的題目以第一個題目搬入、再移除 `activities.topic_id`。
- **與本規格不同之處：** NTNU 的 compose 設定 `RUN_MIGRATIONS=true`，由後端啟動時自動 migrate，而不是「部署前單獨執行 `sqlx migrate run`」。維持現狀，直到維運負責人決定是否改為單獨執行。
- **仍待決定：** 本文件第 3 節的每日加密備份、RPO／RTO 與還原演練是否、何時適用於 NTNU。NTNU 目前的備份與部署前檢查做法見 [`docs/ntnu-ops.md`](../ntnu-ops.md)。

## 2. 監控

| 項目 | 規格 |
| --- | --- |
| 存活檢查 | 既有的 `GET /health`：只表示程序存活 |
| 就緒檢查 | 新增 `GET /ready`：檢查資料庫連線（`SELECT 1`），失敗時回 503 |
| 日誌 | tracing 輸出 JSON，包含 request ID、路由、狀態碼、耗時；**不含**訊息內容、電子郵件、token（S-02.2） |
| 後台查看 | 系統管理者從後台的系統概況與診斷頁查看持久化的失敗事件（見下節）；後台不讀取 Docker socket，成功請求的完整日誌以 Docker stdout 為準。程序記憶體的 request 日誌（`/admin/logs`）已移除 |
| 需要告警的情況 | `/ready` 連續失敗、5xx 比例升高、OpenAI 錯誤率升高、資料庫磁碟使用率超過 80%、備份失敗 |
| 告警通道 | 依部署平台決定（例如 email 或 Discord），至少通知主要與備援負責人 |

### 管理員後台重新安排（2026-11，#450，已決定，已實作：後端 #465／#490、前端 #466／#540、移除記憶體日誌 #544）

- 保留既有帳號與教室管理功能，沿用現有視覺風格，重新安排頁面與資訊。首頁顯示系統概況；帳號管理、教室管理各為獨立頁面。完整後台僅系統管理員可用，教師仍在自己的教室介面管理教室。
- 首頁顯示服務及資料庫狀態、近期 AI 狀態與失敗次數、近期登入失敗及帳號鎖定數、近期待處理錯誤；可進入診斷資訊。AI 失敗數、登入失敗數與帳號鎖定數預設顯示最近 24 小時，並可切換最近 7 天或 30 天。AI 狀態根據首頁選擇的統計期間內的實際呼叫結果：沒有失敗顯示「正常」，至少有一次失敗顯示「有失敗」且可查看詳情，沒有呼叫顯示「尚無資料」；不為健康檢查額外呼叫 AI。
- 診斷紀錄跨服務重啟保留 30 天，到期自動刪除；支援按時間、類型與 request ID 查詢，亦可從帳號或教室頁面查看相關紀錄。以內部識別碼關聯；不存在的帳號無法關聯至既有帳號，但事件仍顯示於全系統診斷清單。
- **診斷事件範圍**：保存 AI 及登入失敗事件與帳號鎖定事件；成功事件用於計算系統狀態與次數，不逐筆顯示在錯誤清單中。
- **失敗詳情**：每筆失敗紀錄至少顯示時間、request ID、失敗分類與發生的功能；AI 失敗另外顯示耗時與重試次數。
- **失敗分類**：AI 包含連線失敗、逾時、key 無效、額度不足、頻率限制、服務異常；登入包含帳號或密碼不符、帳號停用、帳號遭鎖定。管理員可依分類篩選診斷紀錄；使用者端顯示適當的簡短提示。
  - **AI 輸出無法解析（`invalid_output`，2026-11-12 需求方確認採用）**：AI 有回應但內容無法解析（例如主張或總結格式錯誤）時，另記為 `invalid_output`。它與上列的服務端失敗分開：不計入首頁的「AI 失敗次數」與 AI 狀態，單獨以「AI 輸出無法解析」顯示，並可依分類篩選。
- 診斷紀錄不包含密碼、API key、token、學號、電子郵件、聊天原文或其他敏感個資；管理介面與 API 沿用 S-02.1、S-02.2 的遮蔽規則。第一版由管理員主動查看，後台不主動通知；上表的正式維運告警規劃不因此變更。
- **既有的 `/admin/logs` 不保留**：已隨診斷頁上線一併移除 `/admin/logs` 與 `GET /api/admin/logs`（程序記憶體中的 request 日誌，#465）。成功的請求不再有後台可查，完整請求日誌以容器 stdout 為準。
- **儲存與清理**：診斷事件存在 PostgreSQL，統計與查詢都由資料庫計算，所以重啟與多個程序之間結果一致。應用程式內每天執行一次背景刪除，清除超過 30 天的事件；查詢另外限定在最近 30 天內，清理延遲時到期的事件也不會顯示。不引入新的基礎設施。
- **診斷事件欄位**：除了上列必要欄位，另保存路由模板、狀態碼、error code、使用者內部識別碼（可為空，因為登入失敗時帳號可能不存在），AI 失敗另保存模型名稱。**不保存**電子郵件、學號、請求內容與外部服務的錯誤原文；外部服務的錯誤只保存分類，因為原文可能夾帶金鑰或對話內容。
- **稽核**：管理員查看診斷紀錄不另記稽核，因為診斷紀錄不含敏感個資。既有的帳號停用、重設密碼等稽核不變。
- **診斷系統自身失敗時**：寫入診斷事件失敗不得影響原本的請求，只以 tracing 記錄。讀取診斷資料失敗時，概況頁顯示「診斷資料暫時無法讀取」。資料庫連不上時，概況頁仍要能顯示服務正常、資料庫異常，不能整頁失敗。
- **排查範圍**：後台只顯示應用程式內保存的診斷事件，可依 request ID 查單筆。完整的 tracing 日誌留在容器輸出，頁面提示以 request ID 到伺服器日誌查詳情，對應本文件現有的維運流程；不在後台重做日誌搜尋。

## 3. 備份與還原

| 項目 | 規格 |
| --- | --- |
| 方式（與平台無關） | 每日一次 `pg_dump --format=custom`，加密後存到資料庫主機以外的位置 |
| 方式（採託管服務時） | 優先使用平台的自動備份與 point-in-time recovery，每日 dump 作為第二層 |
| 保留 | 每日備份保留 7 份、每週備份保留 4 份；更舊的自動刪除，讓已刪除的資料在約 5 週內自然淡出（對應 S-02.5） |
| 加密 | 備份檔以加密金鑰加密，金鑰與備份分開保存 |
| 還原演練 | 每 6 個月至少一次，並在第一次正式上線前做一次：把備份還原到隔離環境，執行 migrations 與一組資料檢查查詢，記錄耗時與結果 |
| 還原目標 | 資料損失最多 24 小時（RPO），還原時間 4 小時內（RTO）；採用 PITR 時 RPO 可以縮短 |

## 4. 負責人

| 角色 | 職責 | 人選 |
| --- | --- | --- |
| 維運負責人 | migration 審核與執行、備份監控、還原演練、告警處理 | 待指定 |
| 備援負責人 | 維運負責人不在時代理 | 待指定 |

**資料庫與備份的原文存取（已確認，2026-09-29）**
- 系統管理者可以直接存取資料庫與備份，因此讀得到對話原文；不另外區分「維運人員」角色，也不做應用層欄位加密。
- 應用程式的管理介面、API、報表、匯出與日誌仍以 `message` 遮蔽訊息（S-02.2）。
- 資料庫與備份的存取僅限系統管理者，每次存取都留紀錄；隱私說明需告知學生這一點。
- 備份仍建議加密（見第 3 節），用來防止備份檔外洩，而不是用來限制系統管理者。

## 5. 故障情境

| 情境 | 預期處理 |
| --- | --- |
| 資料庫無法連線 | `/ready` 失敗、API 回 503 JSON 錯誤；告警；恢復後自動重連（連線池） |
| migration 失敗 | 部署中止、舊版持續服務；修正後重新部署 |
| 誤刪或資料毀損 | 依最近的備份（或 PITR 時間點）還原到新資料庫，驗證後切換；記錄事件 |
| 備份失敗 | 告警；當日內人工補做備份 |
| 資料庫憑證外洩 | 立即在部署平台輪替憑證並重新部署；檢查存取紀錄 |

## 6. 確認結果

1. **待定**：維運負責人與備援負責人的人選。
2. 備份以公鑰加密（例如 `pg_dump | age -r <公鑰>`），私鑰離線保存，由 2 位指定的系統管理者各持一份；每次解密或還原都留紀錄。
3. RPO 24 小時、RTO 4 小時。
4. 還原演練每 6 個月一次，並在第一次正式上線前做一次。
