# S-09.3.2 後台：服務健康度與端點監控（草案）

> **狀態：草案，待需求方確認。** 本文件是對 S-09.3「管理員後台重新安排」（#450、F-33）的擴充提案。標示「待確認」的項目是建議值，**未經需求方確認前不得寫成驗收條件，也不得開始實作**。確認後依 [CONTRIBUTING.md](../../CONTRIBUTING.md#規格決策流程) 併入 `decisions.md` 與 [`S-09.3-ops-procedures.md`](S-09.3-ops-procedures.md)，並建立功能葉節點。

## 1. 背景與缺口

- 後台首頁已顯示服務、資料庫、AI 狀態與失敗數（F-33）。但「服務」目前只是固定的 `ok`（程序有回應就算正常），看不出請求有多少在失敗、變慢。
- S-09.3 規定診斷事件只保存失敗（AI、登入、帳號鎖定），成功請求不逐筆保存，且「不在後台重做日誌搜尋」。因此管理員目前**無法回答**：「哪個端點在出錯？」「哪個端點變慢？」「這個端點最近有沒有人用？」
- 後端的 request middleware 已經對每個請求算出路由模板、狀態碼與耗時（`lib.rs` 的 `request_id` 層、`access_log.rs`），只是沒有彙整保存。

## 2. 需求（來自需求方）

後台需要：

1. **服務健康度**：一眼看出服務目前是否健康。
2. **端點清單（能監控狀態）**：列出系統的端點，並顯示各端點目前的狀態。

## 3. 提案

### 3.1 服務健康度（首頁新增區塊）

沿用首頁的統計期間選擇（24 小時、7 天、30 天，預設 24 小時）。

| 項目 | 內容 |
| --- | --- |
| 整體狀態 | 正常／降級／異常，由下列指標與門檻決定（見下） |
| 請求量 | 期間內請求總數 |
| 5xx 比例 | 5xx 數 ÷ 請求總數 |
| 延遲 | 全部端點合併的 p50、p95 耗時 |
| 資料庫 | 連線狀態與 `SELECT 1` 回應時間（現有 `status` 已量測） |
| 連線池 | 使用中／閒置／上限 |
| 程序 | 啟動時間（uptime）、版本（git commit 短碼） |
| 維護模式 | 是否開啟（S-15） |
| 背景工作 | 每日診斷清理最近一次成功時間 |

- **待確認：整體狀態門檻。** 建議：資料庫不可用或 5xx 比例 ≥ 5% → 異常；5xx 比例 ≥ 1%、p95 ≥ 3 秒、或清理超過 48 小時未成功 → 降級；其餘正常；期間內請求數為 0 → 顯示「尚無資料」（與 AI 狀態一致）。
- 沿用既有規則：資料庫連不上時整頁仍要能顯示「服務正常、資料庫異常」；讀取統計失敗顯示「統計資料暫時無法讀取」，不能整頁失敗。

### 3.2 端點清單（新增後台分頁「端點」）

**清單來源**：後端的 OpenAPI 文件（`GET /api/openapi.json` 同一份）。現有測試已確保每條路由都收錄在其中，所以沒有流量的端點也會出現在清單。`/ready` 已收錄；`/health` 目前沒有 `#[utoipa::path]`，實作時要補上，清單才完整。

**每列欄位**：

| 欄位 | 說明 |
| --- | --- |
| 方法與路由模板 | 例如 `GET /api/summaries/{id}`；只含模板，不含實際 ID 或查詢字串 |
| 功能分組 | OpenAPI 的 tag |
| 存取限制 | 公開／登入／教師／管理者（取自 OpenAPI security 與 handler 的授權） |
| 請求數 | 選定期間內 |
| 4xx／5xx 數與 5xx 比例 | 4xx 是用戶端錯誤，**不計入端點失敗**，只顯示 |
| 延遲 | p50、p95 |
| 最近請求時間 | |
| 最近一次 5xx 時間 | 可連到診斷頁以 request ID 查詢（只在該事件有診斷紀錄時） |
| 狀態 | 見下 |

**端點狀態**（依選定期間的真實流量被動計算）：

| 狀態 | 條件（待確認的建議值） |
| --- | --- |
| 正常 | 有請求，且 5xx 比例 < 1% |
| 有錯誤 | 5xx 比例 ≥ 1% |
| 異常 | 5xx 比例 ≥ 5%（且 5xx 至少 3 次，避免低流量時一次失敗就誤判） |
| 尚無資料 | 期間內沒有請求 |

**操作**：依狀態、功能分組篩選；依請求數、5xx 比例、p95 排序；搜尋路由；預設把「異常」「有錯誤」排在前面。

**「能監控狀態」的解讀（待確認）：** 建議只做**被動監控**（用真實請求算），理由與 AI 狀態一致：不為健康檢查額外呼叫 AI 或寫入資料。公開的 `/health`、`/ready` 仍由外部探針負責存活監控（S-09.3 告警表）。若需求方要的是**主動探測**（後台定時自己呼叫端點並記錄結果），需另行決定探測哪些端點、頻率、用什麼身分，以及是否會產生資料寫入或 AI 費用，建議不納入第一版。

### 3.3 資料保存

- 在 PostgreSQL 新增每小時彙總表（不引入新基礎設施），主鍵為（小時, 方法, 路由模板）。欄位：請求數、2xx／3xx／4xx／5xx 數、耗時總和、固定分桶的耗時直方圖（用來算 p50／p95）、最近請求時間、最近 5xx 時間。
- 程序內先累加、每 30 秒以 `INSERT ... ON CONFLICT DO UPDATE` 加總寫入，多個程序的結果也一致。寫入失敗不得影響原本的請求，只以 tracing 記錄（與診斷事件相同規則）。程序在兩次寫入之間被殺掉，最多遺失約 30 秒的統計，**可接受**。
- 保留 30 天，沿用每日清理；查詢限定在最近 30 天。
- 沒有對應路由的請求（`<fallback>`）彙整成一列，不讓亂掃的網址撐大資料量。
- 串流（SSE）端點：以串流結尾的 `done`／`error` 事件判定成敗（`access_log::SseOutcome` 已有此資訊）；`error` 事件算該端點的失敗。**待確認**是否所有 `error` code 都算（例如使用者額度用完屬預期的拒絕，是否排除）。

### 3.4 隱私與權限

- 只存路由模板、方法、狀態碼分類與耗時；**不存**使用者識別、IP、實際 URL、查詢字串、request／response 內容。因此不含個資，也不需要遮蔽 `message`。
- 兩個新端點（建議 `GET /api/admin/health` 與 `GET /api/admin/endpoints`）僅系統管理者可用；教師與學生回 `403`，未登入回 `401`。
- 管理員查看不另記稽核（與診斷紀錄相同理由）。
- 維護模式下管理者的請求照常服務（S-15），這兩個頁面不受影響。

### 3.5 不在範圍

- 主動通知與告警（沿用 S-09.3：第一版由管理員主動查看，正式告警規劃不變）。
- 請求日誌搜尋、逐筆請求查看。
- 以使用者、教室為維度的流量統計。
- 外部監控系統（Prometheus、Grafana 等）：不引入未列出的基礎設施。

## 4. 可測試情境（確認後轉為驗收條件）

- Given 管理者開啟後台首頁，When 期間內有 5xx 比例超過門檻，Then 整體狀態顯示降級／異常，並可連到端點清單。
- Given 資料庫連不上，When 管理者開啟首頁，Then 仍顯示服務正常、資料庫異常，端點統計顯示「暫時無法讀取」。
- Given 某端點期間內沒有請求，Then 清單仍列出它，狀態為「尚無資料」。
- Given 某端點有 1 次 5xx 與 2 次成功，Then 因 5xx 少於 3 次不列為「異常」。
- Given 大量請求打到不存在的網址，Then 統計只新增 `<fallback>` 一列。
- Given 兩個程序同時寫入同一小時、同一端點，Then 請求數為兩者加總。
- Given 寫入彙總表失敗，Then 原本的請求照常成功。
- Given 教師、學生、未登入者，When 呼叫新端點，Then 分別得到 `403`、`403`、`401`。
- Given 請求含實際 ID 或查詢字串，Then 彙總表與 API 回應只出現路由模板。
- Given 超過 30 天的彙總資料，Then 不會出現在查詢結果，且被每日清理刪除。
