# S-09.3.2 後台：服務健康度與容器服務監控（草案）

> **狀態：草案，待需求方確認。** 本文件是對 S-09.3「管理員後台重新安排」（#450、F-33）的擴充提案。標示「待確認」的項目是建議值，**未經需求方確認前不得寫成驗收條件，也不得開始實作**。確認後依 [CONTRIBUTING.md](../../CONTRIBUTING.md#規格決策流程) 併入 `decisions.md` 與 [`S-09.3-ops-procedures.md`](S-09.3-ops-procedures.md)，並建立功能葉節點。
>
> 修訂紀錄：初稿提案「端點清單」（逐路由的請求數與錯誤率）；需求方隨後改為「監控各個容器的狀態（tts、asr…）」，本版據此改寫，不再有逐路由統計。

## 1. 背景與缺口

- 後台首頁已顯示服務、資料庫、AI 狀態與失敗數（F-33）。但「服務」目前只是固定的 `ok`（程序有回應就算正常），看不出請求有多少在失敗、變慢，也看不出語音等周邊容器是否還活著。
- 語音對話（cascade）由多個容器組成（見 `docker-compose.yml`）：`cascade-tts`（語音合成）、`cascade-whisper`（語音辨識）、`cascade-adapter`（轉接層）、`cascade`（即時對話）；NTNU 的辨識則可能是主機上的服務。任一個掛掉，學生只會看到語音失敗，管理員無從得知是哪一個。
- 這些容器都已有各自的 HTTP 健康檢查端點（compose 的 `healthcheck`），後端也已經知道它們的位址（`OPENAI_STT_BASE_URL`、`OPENAI_TTS_BASE_URL`、`CASCADE_REALTIME_URL`）。
- S-09.3 規定「後台不讀取 Docker socket」。掛載 socket 等於給應用程式主機 root 等級的權限，本提案維持此規定。

## 2. 需求（來自需求方）

後台需要：

1. **服務健康度**：一眼看出服務目前是否健康。
2. **容器服務清單（能監控狀態）**：列出各個容器服務（例如 tts、asr），並顯示各自目前的狀態。

## 3. 提案

### 3.1 服務健康度（首頁新增區塊）

沿用首頁的統計期間選擇（24 小時、7 天、30 天，預設 24 小時）。

| 項目 | 內容 |
| --- | --- |
| 整體狀態 | 正常／降級／異常，由下列指標與 3.2 的各服務狀態匯總（見下） |
| 資料庫 | 連線狀態與 `SELECT 1` 回應時間（現有 `status` 已量測） |
| 周邊服務 | 3.2 各服務的狀態摘要，例如「4 個中 3 個正常」，並連到服務清單 |
| 連線池 | 使用中／閒置／上限 |
| 程序 | 啟動時間（uptime）、版本（git commit 短碼） |
| 維護模式 | 是否開啟（S-15） |
| 背景工作 | 每日診斷清理最近一次成功時間 |
| 請求量、5xx 比例、p95 耗時 | 期間內全站合計，不分路由（見 3.4） |

- **待確認：整體狀態規則。** 建議：資料庫不可用或 5xx 比例 ≥ 5% → 異常；任一周邊服務異常、5xx 比例 ≥ 1%、p95 ≥ 3 秒、或清理超過 48 小時未成功 → 降級；其餘正常；期間內請求數為 0 → 該項顯示「尚無資料」。語音相關容器只影響語音功能，所以建議只造成「降級」，不造成「異常」。
- 沿用既有規則：資料庫連不上時整頁仍要能顯示「服務正常、資料庫異常」；讀取統計失敗顯示「統計資料暫時無法讀取」，不能整頁失敗。

### 3.2 容器服務清單（新增後台分頁「服務」）

**怎麼知道容器狀態：由後端對各服務的健康檢查端點發 HTTP GET**，不讀 Docker socket。因此「狀態」指的是**服務能不能正常回應**，不是 Docker 層的資訊。

**清單來源：設定。** 新增環境變數 `MONITORED_SERVICES`（JSON 陣列，S-08.3 的環境變數規則），每項包含：

- `name`：識別名稱，例如 `tts`、`asr`、`adapter`、`cascade`；
- `label`：顯示名稱與說明（可多語）；
- `url`：健康檢查位址；
- `impact`：掛掉時受影響的功能，例如「語音回覆」。

未設定時清單只有「資料庫」（用既有的 `SELECT 1`）。清單來自部署設定而非使用者輸入，所以沒有 SSRF 的問題；探測不跟隨轉址、不帶任何 cookie 或授權標頭、只讀狀態碼，**不保存也不顯示回應內容**。

建議的預設對照（依 `docker-compose.yml`，實際位址由各部署的設定決定）：

| name | 容器 | 檢查位址（容器內網路） | 備註 |
| --- | --- | --- | --- |
| `asr` | `cascade-whisper` | `:8101/openapi.json` | NTNU 若用主機服務，改填主機位址 |
| `tts` | `cascade-tts` | `:8100/health` | |
| `adapter` | `cascade-adapter` | `:8103/v1/models` | |
| `cascade` | `cascade` | `:8110/health` | 即時語音對話入口 |

**檢查方式**（待確認的建議值）：後端背景工作每 30 秒對所有服務平行檢查一次，單次逾時 3 秒，2xx 視為正常。**連續 2 次失敗才標為異常**，避免單次抖動。檢查端點都是輕量的健康檢查，不呼叫語音合成、辨識或 AI，不產生費用。

**每列欄位**：

| 欄位 | 說明 |
| --- | --- |
| 名稱與說明 | `tts`／語音合成 |
| 狀態 | 正常／異常／檢查中／尚無資料（剛啟動、尚未檢查過） |
| 受影響功能 | 掛掉時哪些功能會壞 |
| 檢查目標 | 只顯示主機與路徑，不顯示帳密與查詢字串 |
| 回應時間 | 最近一次 |
| 最近檢查時間、最近正常時間 | |
| 目前狀態持續自 | 例如「異常已持續 12 分鐘」 |
| 期間可用率 | 依選定期間，由狀態變化事件計算 |

**操作**：「立即檢查」按鈕（`POST`，僅管理者，限制頻率，例如同一服務 10 秒內最多一次）、依狀態篩選、異常的排在前面、可展開看最近的狀態變化。

**不在清單內**（Docker 層資訊）：重啟次數、CPU／記憶體、容器日誌、容器是否被停掉但沒有健康檢查位址。要看這些需要 Docker socket 或外部監控，**待確認**是否需要（見第 5 節）。完整日誌仍以伺服器 stdout 為準（S-09.3）。

### 3.3 資料保存：只存狀態變化

- 目前狀態與最近一次檢查結果放在程序記憶體，重啟後第一輪檢查前顯示「檢查中」。
- 新增 `service_status_events`（PostgreSQL，不引入新基礎設施）：只在**狀態改變時**寫入一筆（服務名稱、新狀態、時間、檢查失敗的分類），所以資料量很小。分類固定為：連線失敗、逾時、非 2xx 回應；不存回應內容或錯誤原文。
- 寫入前以資料庫中該服務最新一筆事件判斷是否真的是變化，避免多個程序重複寫入。保留 30 天，沿用每日清理。
- 可用率由事件計算：期間內「正常」時間 ÷ 已知時間；第一筆事件之前視為未知，不計入。
- 寫入或讀取失敗不得影響原本的請求，只以 tracing 記錄；讀取失敗時服務頁顯示「狀態資料暫時無法讀取」，仍顯示記憶體中的目前狀態。

### 3.4 全站請求統計（首頁用）

為了顯示請求量、5xx 比例與 p95，在請求完成時（`lib.rs` 的 `request_id` middleware 已算出狀態碼與耗時）累加**全站合計**，每分鐘合併寫入每小時一列的彙總表（請求數、各狀態碼類別數、固定分桶的耗時直方圖）。不分路由、不含使用者與 URL，因此沒有個資；保留 30 天；寫入失敗不影響請求。程序在兩次寫入之間被殺掉，最多遺失約 1 分鐘的統計，可接受。

**待確認：** 若需求方認為首頁不需要請求統計，可整段拿掉，其餘不受影響（此時整體狀態只看資料庫、周邊服務與背景工作）。

### 3.5 隱私與權限

- 新端點（建議 `GET /api/admin/health`、`GET /api/admin/services`、`POST /api/admin/services/check`）僅系統管理者可用；教師與學生回 `403`，未登入回 `401`。
- 不存也不顯示健康檢查的回應內容、使用者識別、IP、聊天內容。
- 管理員查看不另記稽核（與診斷紀錄相同理由）。「立即檢查」不改變任何資料，也不另記稽核。
- 維護模式下管理者的請求照常服務（S-15），這些頁面不受影響。

### 3.6 不在範圍

- 主動通知與告警（沿用 S-09.3：第一版由管理員主動查看，正式告警規劃不變）。
- 啟動、停止、重啟容器等控制動作。
- Docker 層指標與日誌（見 3.2）。
- 逐路由的請求統計與端點清單（初稿提案，已撤回）。
- 外部監控系統（Prometheus、Grafana 等）。

## 4. 可測試情境（確認後轉為驗收條件）

- Given 某服務的健康檢查端點回 2xx，Then 該服務顯示「正常」並帶回應時間。
- Given 某服務連續 2 次逾時，Then 顯示「異常」、失敗分類為逾時，並寫入一筆狀態變化事件；Given 只失敗 1 次，Then 仍顯示「正常」且不寫事件。
- Given 異常的服務恢復，Then 顯示「正常」並寫入一筆事件；狀態沒變時不重複寫入。
- Given 任一周邊服務異常、資料庫正常，Then 首頁整體狀態為「降級」，且可連到服務清單。
- Given 資料庫連不上，Then 首頁仍顯示服務正常、資料庫異常；服務清單仍顯示記憶體中的目前狀態，並提示歷史資料暫時無法讀取。
- Given 沒有設定 `MONITORED_SERVICES`，Then 服務清單只有資料庫。
- Given 設定中有重複的 `name` 或格式錯誤，Then 後端啟動時失敗並指出設定項目（不含 URL 內的帳密）。
- Given 健康檢查回應很大或轉址，Then 不讀取內容、不跟隨轉址，視為非 2xx。
- Given 服務位址含帳密或查詢字串，Then 畫面與 API 只顯示主機與路徑。
- Given 管理者連續點「立即檢查」，Then 超過頻率限制時回 `429`，不會對服務造成壓力。
- Given 教師、學生、未登入者，When 呼叫新端點，Then 分別得到 `403`、`403`、`401`。
- Given 超過 30 天的狀態事件與請求彙總，Then 不出現在查詢結果，且被每日清理刪除。
- Given 寫入狀態事件失敗，Then 原本的請求與探測照常運作。

## 5. 待需求方確認

1. 「容器狀態」是否接受以**健康檢查端點的回應**判斷（建議）？若要 Docker 層資訊（重啟次數、資源、容器是否在跑），需要另行討論掛載 Docker socket 的資安風險，或改用外部監控，建議不納入第一版。
2. 要監控哪些服務？建議 `asr`、`tts`、`adapter`、`cascade`；`db` 已有；`proxy`（nginx）掛掉時管理者連後台都進不去，建議不列入；NTNU 的辨識若是主機上的服務是否也要列。
3. 檢查頻率（建議 30 秒）、逾時（3 秒）、連續幾次失敗才算異常（建議 2 次）。
4. 整體狀態規則：語音相關容器異常只算「降級」是否合適；5xx 比例、p95 的門檻。
5. 首頁是否需要全站請求統計（3.4），還是只要服務與容器狀態。
6. 保留期間是否同診斷紀錄的 30 天。
7. 導覽：新增獨立的「服務」分頁，還是放在系統概況頁內。
