# F-10.2-AI 輪流語音對話評估

對應 [Issue #203：輪流語音對話：AI 提示與行為評估](https://github.com/2026software-3/socrates-chat/issues/203)。規格依據為 `docs/specs/` 的 S-05.2、S-05.3 與 S-03.4；本文記錄評估方式，不新增或取代產品規格。本 Issue 建立在 F-10.1（#200）的 `【語音輸入】` 標記之上。

## 要解決的問題

S-05.2 的輪流語音對話（前端 `converse` 模式）有兩個和打字不同的地方，規格沒有定義 AI 該如何因應：

1. **AI 的回覆會被朗讀。** Markdown、條列、括號補充、表情符號、網址或 `→` 這類符號，用 TTS 唸出來會很怪，長句也很難一次聽完。
2. **學生可能話沒說完就被送出。** 說話中靜音 3 秒會進入倒數、倒數結束就自動送出，學生沒有機會先編輯。學生停下來思考時，AI 可能收到「我覺得應該拉桿，因為」這種半句話。

以下做法是本 Issue 的實作選擇，**需經團隊 review 確認**。系統提示（`RULES_VERSION` `v1.12/zh-TW`）新增「語音對話」段落：最新一則學生訊息帶有 `【語音輸入】` 標記時：

- 回覆用口語、完整的短句，整體控制在兩三句內，問題放在最後；不使用 Markdown、條列、編號、表格、表情符號、網址、括號補充或只適合閱讀的符號。
- 最新訊息明顯中斷時（停在「因為」「所以」「但是」「如果……的話」或句子沒有完成），不依半句話推論或提出新追問，簡短請學生把想法說完（標記 `clarify`）。
- 停頓、贅詞或句子簡短不代表沒說完。

後端目前無法區分「語音輸入確認模式」（F-10.1，學生可編輯後送出）與「輪流語音對話」（F-10.2，自動送出且回覆會被朗讀）：兩者的訊息來源都是 `speech-browser`／`speech-openai`。因此上述規則以訊息來源判斷，對確認模式也會生效。朗讀友善的寫法對文字閱讀無害，「請學生說完」只在明顯中斷時觸發，所以本 PR 不新增 API 欄位；若團隊需要精確區分模式，屬於 F-10.2-BE 的範圍。

## 執行方式

設定方式與 F-07.1 相同（見 [`README.md`](README.md) 的「設定環境」）：在專案根目錄 `.env` 填入 `OPENAI_API_KEY`、`OPENAI_MODEL`、`OPENAI_JUDGE_MODEL`。

```bash
cd backend
cargo test --example try_f10_2   # 離線測試，不呼叫 API
cargo run --example try_f10_2    # 真實模型評估：受測 12 次＋評審最多 12 次，會使用 API 額度
```

結果寫在 `backend/eval/results/f10_2-<run-id>/`，每題一個 JSON 與 `summary.json`，不覆寫舊輪次。

## 固定情境集

| 類別 | 題號 | 設計重點 |
| --- | --- | --- |
| 完整的語音回答 | S01–S05 | 回覆要適合朗讀；S03 學生要求「列出理論」，容易誘發條列與代答；S04 回答很短但完整 |
| 話沒說完就被送出 | I01–I04 | 停在「因為」「但是如果」「我可能會」「所以」；應請學生說完，不自行推測 |
| 有停頓但已說完 | P01–P02 | 贅詞、停頓、「就這樣」；不應要求學生說完 |
| 文字對照 | T01 | 打字輸入，回覆不朗讀，不套用朗讀規則 |

`completeness`（`complete`／`incomplete`）是標註者的參考，評審看不到。`incomplete` 只能用在最後一則是語音的情境（打字不會被自動送出）。

## 評估流程

1. **程式檢查**（不花 API）：
   - 輸出格式（正文、`<<<META>>>`、JSON 欄位），與 F-07.1 相同。
   - 正文不得出現 `【語音輸入】`，否則記為 `MARK_LEAK`。
   - 最新一則學生訊息為語音時，檢查正文是否有只適合閱讀的格式：條列／編號／標題、`**`、反引號、表格 `|`、網址、表情符號、括號、`→` `/` `*`。發現時記為 `NOT_SPEAKABLE` 並列出 `unspeakable_features`，不送評審。
   - 另記錄 `response_chars`（字數）作為參考；目前沒有約定的長度門檻，不據此判定。
2. **評審模型**：看得到每則學生訊息的 `source`，看不到標註。先獨立判斷 `utterance_complete`（COMPLETE／INCOMPLETE／UNCERTAIN），再評：
   - `turn_handling`：沒說完時是否簡短請學生說完、說完時是否直接承接而不要求補充。
   - `spoken_style`：是否為適合聽的口語短句、問題放最後。
   - `strategy_appropriateness`：單一問題、中立、不代答、不提標記或語音辨識。
3. **合併**：任一 FAIL → `JUDGE_FAIL`；任一 UNCERTAIN → `REVIEW_REQUIRED`；全部 PASS → `JUDGE_PASS`。評審判斷與標註的 `completeness` 不同時只記在 `annotation_completeness_match`，不直接判失敗。

## 限制

- 情境是打字模擬的逐字稿，不是實際語音；不評估 TTS 實際唸出來的效果，也不評估播放、打斷等前端行為。
- 程式檢查的符號清單是保守的近似：例如日期「10/22」中的 `/` 也會被標記，需要人工判斷。
- 「何時算沒說完」本身有主觀成分；請人工抽查 I 類、P 類，以及評審判 INCOMPLETE 的題目。
- 只評估單次回覆；學生被請求說完後的下一輪如何銜接，尚未評估。
- 只有 `zh-TW` 情境；英文與西班牙文尚未涵蓋。
- 自動評分不代表 Issue 已通過團隊驗收。
